# D022: Clone Semantics — deepClone / shallowClone

## Status
firm

## Resolves
No object cloning mechanism. Users cannot create independent copies of objects.

## Depends On
- D017 (field-level const — deepClone optimizes const fields)
- D018 (object layout — TypeInfo contains clone function pointers)
- D020 (runtime — ss_shallow_copy provides byte-level copy)

## Decision
Two explicit clone methods, auto-generated by compiler for every class. No `.clone()` alias — users must choose:

**`.deepClone()`** — fully independent recursive copy:
- `int`/`double`/`bool`: direct value copy
- `const` fields and `string` (immutable types): `rc_inc` only (safe to share, optimization)
- Mutable reference-type fields: recursive `.deepClone()` call
- New object gets rc = 1
- Original object's rc unchanged

**`.shallowClone()`** — first-layer copy, internal refs shared:
- All fields copied by value (primitives) or pointer (references)
- Reference-type fields: `rc_inc` (shared, not cloned)
- New object gets rc = 1
- Equivalent to `ss_shallow_copy` + `rc_inc` all ref-type fields

Both dispatched via TypeInfo function pointers (D018). Compiler generates per-class implementations:
- `ss_deep_clone_ClassName` — recursive deep clone
- `ss_shallow_clone_ClassName` — shallow byte copy + rc_inc

**User override:** Users can define custom `.deepClone()` / `.shallowClone()` methods in class body. Compiler uses user implementation instead of auto-generated one.

```
class Player {
    const name: string
    health: int
    weapon: Weapon

    function deepClone(): Player {
        return new Player(this.name, this.health, this.weapon.deepClone())
    }
}
```

## Key Reasoning (3 sentences max)
Forcing explicit `deepClone` vs `shallowClone` eliminates the ambiguity of a single `.clone()` — users always know whether nested objects are shared or independent. The const field optimization (rc_inc instead of copy) is a natural fit since const fields are guaranteed never to be mutated through any reference. TypeInfo dispatch enables generic clone operations without knowing the concrete type at the call site.

## Rejected Alternatives
- Single `.clone()` method: Ambiguous — does it deep or shallow copy? Every language that offers a single clone has footgun stories (Java's `Cloneable`, JS spread operator).
- `.clone()` as alias for `.shallowClone()`: Still ambiguous. Users who want deep copy will forget to call the right method.
- COW (copy-on-write) instead of explicit clone: Adds hidden runtime cost and complexity. Explicit cloning keeps performance predictable (V2).

## Interfaces With Other Decisions
- D017 (field-level const): deepClone skips recursive copy for const fields (rc_inc only).
- D018 (TypeInfo): Clone function pointers stored in TypeInfo for vtable dispatch.
- D019 (Perceus IR): DEEP_CLONE and SHALLOW_CLONE are PIR instructions.
- D020 (runtime): ss_shallow_copy provides low-level byte copy for shallowClone.

## Open Tensions
- deepClone of circular object graphs will infinite-loop. Phase 1 doesn't handle cycles. Could add visited-set tracking in Phase 3.
- Generic containers (List<Player>): deepClone needs to know element type to decide whether to recurse. Requires type info propagation.
